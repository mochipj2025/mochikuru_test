# ヒーロー／ロード画面／ミニゲーム 設計案（実装前レビュー用）

作成日: 2026-08-14
元ブリーフ: `docs/fable-hero-loading-minigame-brief.md`
状態: **実装済み（2026-08-14承認、同日実装・検証完了）**

実装時の設計からの差分:
- 軽量スプライトは256色量子化を追加し、実測 64〜78KB/体（予算250KBの1/3以下）
- 夜空スラのみ原本の行が逆（row1=左向き）だったため walk は row2 を採用
- 歩行フレームは類似度検索の環状順に並び替えて収録（お金スラは周期比 0.59→1.47）
- ベースPetの軽量版は元の行位置(0〜3)を保存し、site-motion.js の座標計算は無変更
- 星雫の5色に形状差（★✦✧◆●）を追加（色覚対応）
- 再プレイ✦ボタンは鉢植えのタップ領域と重なったため、鉢の左隣へ移動

## 1. 現行コードとアセットの診断

### 1-1. 構成の確認（ブリーフとの照合）

ブリーフ記載の構成は実コードと一致していた。追加で分かった事実を挙げる。

| # | 発見 | 影響 |
|---|---|---|
| D1 | `assets/mochisura-pet.webp`（2.40MB）は `site.css` の `background-image` で参照され、**現状でもクリティカルパスに乗っている**（`.pet-sprite`、1536×1728、8列9行、セル192px） | 初期予算700KBはこの1枚だけで超過。ローダーを付けても根本は直らない |
| D2 | `character-selector.js` は初期化時に**カード表5枚＋裏1枚（合計約1.58MB）を即生成・即ロード**する。ビューポート外でも待たない | ヒーロー表示前の帯域を食う。`loading="lazy"` 1行で解決可能 |
| D3 | `site-motion.js` は鉢植え12段階（約600KB のPNG群）を初期化時に全て `new Image()` で先読みする | 初期帯域の圧迫。`requestIdleCallback` へ遅延可能 |
| D4 | 常駐rAFループは現状2本: `galaxy.js` の `render()`（全画面Canvas再描画＋shadowBlur、毎フレーム）と `site-motion.js` の `animatePet()` | rAFはタブ非表示で自動停止するので受け入れ条件「非表示中の停止」は実質満たす。`galaxy.js` の `setInterval`（60s）だけ残るが無害 |
| D5 | `site.css` に **未使用の `.hero-cameo` 一式**（237〜290行、724行）が残っている。img＋ラベルspan＋昼夜対応という構造で、今回のゲスト表示とほぼ同型 | 過去のカメオ実験の残骸。削除ではなく**ゲスト表示の下敷きに再利用**するのが最短 |
| D6 | 昼夜連携は `mochisura:sky-mode` CustomEvent（site-motion発火→galaxy受信）と `localStorage: mochisura-garden-night` で成立済み | ゲストの昼夜対応はこのイベント購読だけでよい。新規の状態管理は不要 |
| D7 | 育成データは `localStorage: mochisura-growth-v1`。ゲスト機能はこのキーに一切触れない設計にする | 破壊禁止事項に対応 |
| D8 | テストは `tests/*.js` を素のNodeで個別実行する静的検査（DOM無し）。`test-navigation.js` は**全HTMLの href/src 実在チェック**を走らせる | 新規HTML参照はファイル実在が必須。manifest経由のJS参照は対象外 |
| D9 | キャッシュバスターは `?v=YYYYMMDD-name` 規約 | 新規ファイルも同規約に従う |
| D10 | ローダーは現状存在しない。CSS 3枚（合計約63KB）がレンダーブロック。回線が細いと無地の時間が出る | ローダーHTML＋クリティカルCSSの**インライン化**が必要 |
| D11 | v2原本の実測: 夜空3.61MB / お金3.28MB / 相性3.10MB / 毒舌3.08MB / カード3.54MB（合計16.6MB、ブリーフ値より微増） | 一括ロード禁止の前提は変わらず |

```text

 ▼

 │  ├─(3個到達)→ 「だれかが庭へ向かっています…」表示           │
 │  ├─(t≧4s && 重要素材未完)→ 「庭へ入る（静止画）」強制点灯   │

 │                                                        │

 │                     │ ユーザー押下 or ゲーム終了後1.2s自動  │
 ▼                     ▼                                  │
ASSET_ERROR         TRANSITION_TO_GARDEN ◀────────────────┘
 │ 静止画/CSSシルエット │ 星雫→庭へ落ちるクロスフェード(600ms)
 │ へフォールバックし    │ ローダーDOM除去・抽選結果を sessionStorage へ
 │ 同じ遷移へ合流       ▼
 └──────────▶ HERO_IDLE（既存の庭が完全動作）
                │ 最初のユーザー操作から2〜4s
                ▼
              GUEST_LOADING（選出1体の軽量スプライトをfetch+decode）
                │ decode成功            │ 失敗
                ▼                      ▼
              GUEST_ENTER(0.6s)      （ゲスト中止・庭は通常のまま）
                ▼
              GUEST_INTERACTIVE（8〜12s滞在、タップで詳細）
                │ タイムアウト/閉じる     │ CTA押下
                ▼                      ▼
              GUEST_EXIT(0.5s)        対応ページへ遷移（通常のaクリック）
                ▼
              HERO_COOLDOWN（45〜90s乱数）── 再登場は1セッション最大2回
                └─(2回目終了)→ 以後は星雫再プレイボタンのみ
```

**重要素材（進捗の分母）** は次の5点。架空タイマーは使わない。

1. DOM準備（`DOMContentLoaded`）
2. 重要CSS適用（インラインCSSなので実質即時＝初期値に含める）
3. ヒーロー背景準備（CSSグラデのみ＝DOM到達で完了扱い）
4. ベースPet軽量スプライトの `decode()` 完了
5. ヒーロー初期化完了（`site-motion.js` 実行済みシグナル）

進捗は 5項目の重み付き合算（10/10/10/50/20%）。`aria-valuenow` の読み上げ更新は10%刻み。

## 4. ミニゲーム「星雫あつめ」8秒シーケンス

| 時刻 | 画面 | 内部 |
|---|---|---|
| 0.0s | ローダー即表示（インラインHTML+CSS）。門とシルエットがフェードイン | 開始時刻記録。重要素材の読込は既に進行中 |
| 0.7s | 未完了なら星雫3個が漂い始める（1個ずつ120ms差で出現） | 5色から重複なしで3色を初期配置 |
| 0.7〜8.0s | タップ/Enter/Spaceで収集。吸い込み0.3s→カウンタ更新→新しい星雫が1個補充（常時3個、色は5色ローテ） | 収集ごとに色を記録。`aria-live` で「星雫を2個あつめた」 |
| 3個目収集時 | 「だれかが庭へ向かっています…」＋門の光がわずかに強まる | **抽選確定**（§5）。当選ゲストのスプライトを即 `fetch` 開始 |
| 素材完了時（随時） | 「庭へ入る」が金色に点灯。ゲーム続行は自由 | CRITICAL_READY |
| 4.0s | 素材未完なら「庭へ入る（静止画）」を強制点灯 | 失敗時の脱出保証 |
| 8.0s | 星雫がゆっくり門へ吸い込まれゲーム終了。以後は進捗表示のみ | 収集0個でも成立（抽選は乱数へ） |
| 終了+1.2s | ユーザー未操作なら自動で庭へクロスフェード | TRANSITION_TO_GARDEN |

- 星雫は `<button class="stardrop">`。Canvas・物理エンジン不使用。移動はCSS `transform` アニメ（各12〜18s周期の楕円軌道、`prefers-reduced-motion` では静止）
- 連打煽り・スコア・失敗の概念なし。取れなくても何も損しない

## 5. ゲスト抽選ルール

```text
入力: collected = {navy:2, white:0, pink:1, ...}（ゲーム収集色）
      ゲーム未実施（QUICK_EXIT）の場合は collected = 空

1. collected が空 → 5体から等確率で1体
2. 最多色が単独 → 60%でその色のキャラ、40%で5体等確率（当選キャラ含む再抽選）
3. 最多色が同数複数 → 5体から等確率

保存: sessionStorage["mochisura-hero-guest-v1"] =
      { id, decidedAt, appearances: 0 }
同一セッション内はこの結果を再利用（リロードしても同じ子が来る）。
タブを閉じれば消える。localStorageは使わない。
```

色→キャラ対応（ブリーフ通り）: 紺金=夜空 / 白金=お金 / 桃薄紫=相性 / 紫青=毒舌 / 青緑金=カード

登場規則（ブリーフ通り＋具体化）:

- 同時1体。初回は**最初のユーザー操作**（ヒーロー内 pointerdown / keydown / 最初のスクロール）から2〜4s後
- 滞在8〜12s → 退場 → 45〜90s乱数のクールダウン → 再登場。**1セッション最大2回**（`appearances` で管理）
- タップ1回目=吹き出し（名前・役割・CTA・「また今度」）、CTA押下でのみ遷移。自動遷移なし
- 吹き出し表示中は滞在タイマー停止（読んでいる途中に消えない）
- 登場中はベースPetを待機化: `mochisura:guest` イベント `{phase:'enter'|'exit'}` を発火し、`site-motion.js` 側に約10行の購読コードを追加（歩行目標をクリアしidleへ）。鉢植え操作は止めない
- 昼夜: `mochisura:sky-mode` を購読し、夜は `brightness(.92)`＋影色変更のみ。画像は増やさない
- キャラ別演出はブリーフの表の通り（各0.4〜0.9s、transform/opacityのみ、1回きり）

エントリーポイント（1キャラ1箇所固定）:

| キャラ | 入口 |
|---|---|
| 夜空スラ | 左の丘の上（星座線が1本つながってから降りる） |
| お金スラ | 中央の草むらから跳ねて出る |
| 相性スラ | 2つの光が合わさった場所に着地 |
| 毒舌スラ | 画面右端からスッと歩いて入る |
| カードスラ | 浮いたカードの陰から現れる |

## 6. アセット表と容量目標

### 6-1. 新規作成: 軽量ランタイムスプライト

原本 `pet-runs/*/final/spritesheet.webp`（1536×2288、セル192×208）から**必要行のみ nearest-neighbor で1/2縮小**して抽出。原本は変更しない。生成には既存の pixelart MCP（inspect / export / check_walk）を使い、抽出後に歩行検算を通す。

```text
assets/hero-pets/
├ manifest.json          … 全定義（下記）
├ base-idle-walk.webp    … ベースPet軽量版（mochisura-pet.webp 0〜3行から抽出）
├ yozora-idle-walk.webp
├ okane-idle-walk.webp
├ aisho-idle-walk.webp
├ dokuzetsu-idle-walk.webp
└ card-idle-walk.webp
```

各ゲストシートの収録（セル96×104、8列3行=768×312px、24フレーム以内）:

| 行 | アニメ | フレーム | 出典行 |
|---|---|---|---|
| 0 | idle | 6 | 原本0行 |
| 1 | walk-right | 8 | 原本1行 |
| 2 | greeting 4 + surprise 4 | 8 | 原本3・4行 |

**walk-left は収録せず CSS `transform: scaleX(-1)` で反転**（未決Q2）。これで24→16実フレーム相当になり容量が約2/3に落ちる。

manifest.json（JS からのみ参照。HTMLに書かないので `test-navigation.js` と干渉しない）:

```json
{
  "cell": { "w": 96, "h": 104 },
  "characters": {
    "night": {
      "sheet": "yozora-idle-walk.webp",
      "href": "slime/index.html",
      "anims": {
        "idle":     { "row": 0, "frames": 6, "fps": 8 },
        "walk":     { "row": 1, "frames": 8, "fps": 10, "mirrorLeft": true },
        "greeting": { "row": 2, "frames": 4, "fps": 7 },
        "surprise": { "row": 2, "frames": 4, "col": 4, "fps": 9 }
      }
    }
  }
}
```

### 6-2. ロード区分と予算

| 区分 | アセット | 目標容量 | タイミング |
|---|---|---:|---|
| クリティカル | index.html＋インラインローダーCSS/JS | +8KB以内 | 即時 |
| クリティカル | site.css / galaxy.css / character-selector.css | 実測63KB | 即時（現状維持） |
| クリティカル | `hero-pets/base-idle-walk.webp` | **≦180KB** | 即時（旧2.40MBを置換） |
| クリティカル | 鉢植え現在段階1枚（例 me.png） | 54KB | 即時 |
| 準クリティカル | loading/hero-experience の JS/CSS 4本 | 合計≦24KB | defer |
| 遅延1 | 当選ゲスト1体のシート | **≦250KB** | 抽選確定直後にfetch |
| 遅延2 | リンクカード6枚（1.58MB） | 現状維持 | `loading="lazy"`（ビューポート接近時） |

| 禁止 | `pet-runs/` 原本・v2フル5体 | — | preload禁止。実行時参照もしない |

**予算合計**: クリティカル画像 約234KB（目標700KB以下 ✅）、初回操作可能まで 約330KB（目標1.2MB以下 ✅）。現状の実測約4.7MB（pet 2.4MB＋カード1.58MB＋鉢植え600KB＋…）から**約93%削減**。

## 9. パフォーマンス予算と測定方法

### 予算（ブリーフ準拠）

| 指標 | 目標 | 設計上の見込み |
|---|---|---|
| 初期クリティカル画像 | ≦700KB | 約234KB |
| 初回操作可能までの転送 | ≦1.2MB | 約330KB |
| LCP | ≦2.5s | ローダー見出しorヒーローコピー（テキスト）なので大幅短縮 |
| CLS | ≦0.05 | ローダーは全画面固定オーバーレイ、ゲストは `position:absolute` でレイアウト非関与 → 加算ゼロ |
| 長時間タスク | <50ms | manifest解析・decode は分割。抽出画像が小さいためdecodeも短い |
| 常駐rAF | 増加ゼロ | 新規ティッカーはゲスト表示中のみ稼働 |

### 測定方法

1. ローカル: `npx serve` 等の静的サーバ＋Chrome DevTools Lighthouse（モバイル設定）を実装前後で取得し比較
2. スロットリング検証: DevTools「Slow 4G / 4x CPU」で ①700ms分岐 ②4s失敗脱出 ③8s終了 の3タイマーを目視＋`performance.mark` ログで確認
3. 転送量: Network パネルで「Load」時点の transferred を記録（クリティカル）、アイドル10s後を記録（遅延分）
4. 回帰: 既存の昼夜切替・育成・カルーセルをスロットリング下で操作しジャンクがないこと
